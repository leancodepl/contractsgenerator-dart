# leancode_contracts_serializable

`json_serializable` extended so it can serialize **generic** contract types
(`PaginatedResult<T>`, `Foo<SomeEnum>`, nested generics) generated by
`leancode_contracts_generator` — which stock `json_serializable` cannot
(issue #95).

## Why

`json_serializable` only forwards per-argument factories to a field type's
`toJson` when it has required positional parameters. Contract generics have no
`toJson` (dropped to keep inheritance) or an optional one, so a field like
`final PaginatedResult<SomeEnum> page;` fails the build
(`Could not generate toJson code`) or silently emits raw enums.

`ContractsGenericTypeHelper` drives off the field's own type arguments and calls
the generated `_$<Name>ToJson`/`_$<Name>FromJson` free functions with factories
composed recursively — regardless of the type's `toJson`.

## Usage

**Option A — replace `json_serializable` (no build.yaml):**

```yaml
dev_dependencies:
  build_runner: ^2.8.0
  leancode_contracts_serializable: ^0.1.0   # instead of json_serializable
```

The builder auto-applies; stock json_serializable doesn't run because you no
longer depend on it directly. This builder is a superset, so your own
`@JsonSerializable` classes keep working too.

**Option B — keep `json_serializable` alongside (needs build.yaml):**

If something else in your project needs `json_serializable` as a direct
dependency, keep it and swap only the builder:

```yaml
dev_dependencies:
  json_serializable: ^6.14.0
  leancode_contracts_serializable: ^0.1.0
```

```yaml
# build.yaml
targets:
  $default:
    builders:
      json_serializable: {enabled: false}
      leancode_contracts_serializable: {enabled: true}
```

Leaving both builders enabled makes them conflict on the shared `.g.dart` part.

## Assumption

Contracts live in one library (`contracts.dart` + its `part`), so the private
`_$…` functions are reachable. This holds for `leancode_contracts_generator`.
